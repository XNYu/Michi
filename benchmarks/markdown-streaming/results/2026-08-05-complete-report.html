02

为什么 CPU 会差这么多

work amplification + blockers

优势来自“减少昂贵工作的触发次数”，而不是某个 Markdown parser 单次快数倍。Streamdown Word/Char 在 chunk 到来时频繁重分块、重渲染和执行插件；Michi 把语义重解释限频，tail 只做短文本状态更新。

1
解析调度解耦
chunk arrival 不再等于 full parse。3Hz snapshot 把 parse 次数从“更新次数级”降到“时间窗口级”。
2
稳定前缀复用
已提交 block 不反复进入 Markdown pipeline；pending tail 短且 append-only，可复用 carry/state。
3
重插件限频
Shiki、Mermaid、KaTeX、controls 和 unified pipeline 只在 snapshot 变化时追赶，不在每个 chunk 上重跑。

剩余风险是 burst，不是总量：Hybrid code-heavy 512 出现一次约 250ms 最大 frame，128 档 code-heavy 有 5 个 long tasks；Math/HTML 也会在 snapshot 时集中追赶。总 CPU 已下降，但同步执行重插件仍可能产生肉眼可见的单次停顿。
生产化建议顺序next
Shiki fence-close / idle
流式 fence 未闭合时先渲染轻量 code body；闭合或浏览器 idle 后再做完整 syntax highlight。
Mermaid fence-close + viewport
只有闭合且进入 viewport 的 Mermaid fence 才动态 import 与渲染 SVG；离屏内容延迟。
Heavy plugin frame budget
将插件工作拆到多个 frame / scheduler task，限制单次 snapshot 的同步预算。
最后再接生产 renderer
当前代码仅在 benchmark harness；完成 burst 优化与真实 Michi pane 视觉验收后再决定替换路径。
